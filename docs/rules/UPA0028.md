# UPA0028 — Value type used as collection key without IEquatable

> English | [繁體中文](UPA0028.zh-TW.md)

| | |
|---|---|
| Category | Performance |
| Default severity | Warning |
| Enabled by default | Yes |

## Cause

A struct is used as the key of a hashed collection — `Dictionary<TKey, TValue>`,
`HashSet<T>`, `ConcurrentDictionary<TKey, TValue>` — or searched for in a `List<T>` or array
via `Contains`, `IndexOf`, `Remove`, `Array.IndexOf` or `Array.Contains`, and the struct does
not implement both `IEquatable<T>` and an override of `GetHashCode`.

Unlike most performance rules here, this one is not limited to per-frame code: a lookup on a
badly-keyed dictionary costs the same wherever it happens.

## Rule description

[`EqualityComparer<T>.Default`](https://learn.microsoft.com/dotnet/api/system.collections.generic.equalitycomparer-1.default)
chooses its implementation from the type: it "uses the `IEquatable<T>` generic interface … if
type `T` implements it". A struct that does gets a comparer calling the typed `Equals`, with
no allocation. A struct that does not gets one calling `object.Equals(object)`, which boxes
both operands on every comparison.

It gets worse when the struct also does not override `Equals`. The inherited
[`ValueType.Equals`](https://learn.microsoft.com/dotnet/api/system.valuetype.equals) then
compares "field by field" using reflection for any struct whose fields are not all blittable
— slow as well as allocating. `GetHashCode` behaves the same way, which is why both members
are needed: implementing only one still leaves a cost on every lookup.

This project measured it in the sandbox across Mono and IL2CPP on Unity 2022.3 and Unity 6.
Over 200,000 `ContainsKey` calls, a plain struct key resolved to `ObjectEqualityComparer<T>`
and allocated (9–20 gen-0 collections during the run); the same struct with `IEquatable<T>`
and a `GetHashCode` override resolved to `GenericEqualityComparer<T>` and allocated nothing.

Enums are not reported. The same measurements confirm the runtime has dedicated non-boxing
comparers for them — see [Enum dictionary keys](enum-dictionary-keys.md). Type parameters are
not reported either, since whether they box depends on the instantiated type.

The diagnostic is reported at the use site, with the struct declaration as a secondary
location. A struct declaration cannot tell you whether it is ever used as a key, so reporting
there would bury real findings under advice for plain data structs.

## How to fix violations

Implement both members on the struct.

Before:

```csharp
public struct GridCoord
{
    public int X;
    public int Y;
}

readonly Dictionary<GridCoord, Tile> tiles = new Dictionary<GridCoord, Tile>();
```

After:

```csharp
public readonly struct GridCoord : IEquatable<GridCoord>
{
    public readonly int X;
    public readonly int Y;

    public bool Equals(GridCoord other) => X == other.X && Y == other.Y;

    public override bool Equals(object obj) => obj is GridCoord other && Equals(other);

    public override int GetHashCode()
    {
        unchecked
        {
            return (X * 397) ^ Y;
        }
    }
}
```

`System.HashCode.Combine` is a cleaner way to write `GetHashCode`, but its availability
depends on the project's API Compatibility Level, so the prime-multiplication form above
works everywhere.

If you cannot change the struct — it comes from a package, say — pass an
`IEqualityComparer<T>` to the collection's constructor instead. The rule does not report a
construction that supplies one.

## When to suppress warnings

Suppress when the collection is tiny and short-lived, or when the struct is a third-party
type you cannot change and supplying a comparer is not worth the code.

## How to configure or suppress

- Single site: wrap it in `#pragma warning disable UPA0028` / `#pragma warning restore UPA0028`
- Whole project: set `dotnet_diagnostic.UPA0028.severity = suggestion` (or `none`) in `.editorconfig`
- By path: note that the shipped `editor-relaxed` presets deliberately keep this rule at its
  normal severity — being in editor code does not make a struct any better as a key

## Configuration

None. This rule has no options and is not hot-path scoped.

## Related rules

- `CA1815` asks every public struct to override `Equals` and `operator ==`, regardless of how
  it is used, and does not ask for `IEquatable<T>`. This rule fires only where the struct is
  actually used as a key. Consider setting `CA1815` to `none` when this rule is enabled.
- UPA0026 reports boxing from calling an inherited `ToString`/`GetHashCode`/`Equals(object)`
  on a value type directly. The two do not overlap: there, the boxing call is visible in your
  code; here, it happens inside the collection.
- [Enum dictionary keys](enum-dictionary-keys.md) explains why the enum version of this
  advice no longer applies.
