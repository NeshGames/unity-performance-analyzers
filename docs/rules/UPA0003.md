# UPA0003 — String-based shader or animator property access

> English | [繁體中文](UPA0003.zh-TW.md)

| | |
|---|---|
| Category | Performance |
| Default severity | Warning |
| Enabled by default | Yes |

## Cause

A string-based overload of `Material.Set*/Get*/HasProperty`,
`MaterialPropertyBlock.Set*/Get*`, `Shader.SetGlobal*/GetGlobal*`, or
`Animator.Play/CrossFade/CrossFadeInFixedTime/Set*/Get*/ResetTrigger` is called with a name
argument that is a string literal or compile-time constant.

## Rule description

These APIs accept either a property/state name string or an integer ID. The string
overloads convert the name to the ID on every call; the integer overloads skip the
conversion entirely. Unity provides `Shader.PropertyToID` and `Animator.StringToHash` to
perform the conversion once so the resulting ID can be reused.

The rule is **not** limited to hot paths by default: the string is resolved on *every* call,
whether or not the call sits in `Update`, and these APIs are almost always called
repeatedly — material updates, effect parameters, animation state changes. Scoping it to hot
paths would miss the calls one level away from a per-frame method, which is where they
usually are. Set `upa_shader_property_hot_path_only = true` to narrow it.

Calls whose name argument is a non-constant expression are not reported — the value may be
data-driven and cannot be statically cached. `Shader.PropertyToID` and
`Animator.StringToHash` themselves are never reported. Shader keyword APIs
(`EnableKeyword` etc.) are out of scope in v0.1.

Setup that runs once is not reported either: constructors and field initialisers, `Awake`
and `Start`, and methods invoked from the inspector with `[ContextMenu]`. The claim holds
there — the string really is resolved on every call — but there is only ever one call, so
caching the id into a new field is churn for nothing. On three real games this shape was
eleven of the rule's fourteen findings.

`OnEnable` is **not** in that set, and the difference matters. `Awake` runs once in an
object's life; `OnEnable` runs on every reactivation, and object pooling — which
[UPA0031](UPA0031.md) recommends — reactivates objects constantly. A pooled bullet's
`OnEnable` runs about as often as bullets are fired. `OnDisable` and `OnDestroy` are absent
for the same reason: the test is "runs once in the object's life", not "is named like a
lifecycle method".

Editor-only methods are skipped as well — `OnDrawGizmos`, `OnDrawGizmosSelected`,
`OnValidate`, and methods marked `[MenuItem]`, `[InitializeOnLoadMethod]` or
`[DidReloadScripts]`. A player build never calls them, so what they cost there is nothing.
`Reset` is deliberately not in that list: Unity calls its own `Reset` only in the editor, but
`Reset()` is also the usual name for returning a pooled object to its starting state, and that
one runs every frame.

## How to fix violations

Resolve each name once into a `static readonly int` and use the integer overloads.

Before:

```csharp
class Effect : MonoBehaviour
{
    void Apply(Material mat)
    {
        mat.SetFloat("_Alpha", 0.5f);
        _animator.Play("Idle");
    }
}
```

After:

```csharp
class Effect : MonoBehaviour
{
    private static readonly int Alpha = Shader.PropertyToID("_Alpha");
    private static readonly int Idle = Animator.StringToHash("Idle");

    void Apply(Material mat)
    {
        mat.SetFloat(Alpha, 0.5f);
        _animator.Play(Idle);
    }
}
```

Shader properties and animator states hash through different functions —
`Shader.PropertyToID` and `Animator.StringToHash`. They are not interchangeable.

A project-wide `static class ShaderProperty { ... }` holding every id is a common
convention and works just as well; the saving is the same either way, since the string is
hashed once rather than on every call. That is a structure choice; follow the convention the
project already uses.

When caching a **string literal** in the type that makes the call, name the field after the
literal with the leading underscore removed — `"_PositionBuffer"` becomes `PositionBuffer` —
and append `Id` if that name already means something where the call sits. This is not rare:
`"_Color"` is a common property name, and a field called `Color` would shadow
`UnityEngine.Color` for the whole type, so `"_Color"` becomes `ColorId`. Declare one field
per name per type, not one per call: a single effect file can hold dozens of these calls
across a handful of distinct names.

When the name is already a compile-time constant that is not a literal, keep the constant —
it is often the project's own way of keeping the name in one place — and hash it:

```csharp
const string AlphaProperty = "_Alpha";
static readonly int Alpha = Shader.PropertyToID(AlphaProperty);
```

## When to suppress warnings

Suppress in one-off editor tooling or debug utilities where the call count is trivial, or
when a property is intentionally accessed exactly once during initialization and a cache
class would add indirection without benefit.

## How to configure or suppress

- Single call site: wrap it in `#pragma warning disable UPA0003` / `#pragma warning restore UPA0003`
- Whole project: set `<Rule Id="UPA0003" Action="Info" />` (or `None`) in `Assets/Default.ruleset`
- By assembly: place a custom `Default.ruleset` in that asmdef folder and set this rule to `None`; it overrides the project-wide ruleset for that assembly
- Scope: set `upa_shader_property_hot_path_only = true` to limit the rule to per-frame hot paths

## Configuration

Set analyzer options in `Assets/Rules.UnityPerformanceAnalyzers.additionalfile`.

```ini
# Narrow the rule to per-frame hot paths only (default: false)
upa_shader_property_hot_path_only = false
```

## Related rules

- `UNT0041` (Microsoft.Unity.Analyzers) covers repeated string-based `Animator` calls only
  when it detects the repetition. UPA0003 reports any constant-string usage, so the two can
  coexist; set one of them to `None` in the ruleset if the overlap is unwanted.
