# UPA0006 — Reference type allocated in per-frame method

> [English](UPA0006.md) | 繁體中文

| | |
|---|---|
| 類別 | 效能 |
| 預設嚴重度 | 警告(Warning) |
| 預設啟用 | 是 |

## 成因

在每幀熱路徑內發生了 managed 堆積(heap)配置:建立參考型別物件
(`new List<int>()`)、建立陣列(`new int[16]`)、對值型別做 boxing 轉換
(`object o = 42;`,或把 struct 傳給 `object` 或介面型別的參數),
或字串插值中的值型別插值洞(`$"hp {hp}"` 且 `hp` 為 `int`)。

## 規則說明

Unity 的垃圾回收器是非分代式(non-generational)的:回收成本隨整個 managed 堆積
的大小增長,而回收時機由配置速率決定。因此每幀配置會表現為週期性的幀尖峰,
且其發生時機不受你控制。讓熱路徑保持零配置是標準紀律,本規則就是在落實它。

boxing 之所以納入,是因為它是最隱形的配置——原始碼裡沒有 `new`。
它常藏在轉換成 `object` 或介面參數、非泛型集合,
以及把 `enum` 值傳給非泛型 API 的地方。
字串插值的插值洞是同一種陷阱:編譯器把 `$"hp {hp}"` 降階(lower)為引數型別是
`object` 的 `string.Format` 呼叫,`int` 因此被 box。Unity 的垃圾回收指引特別點名
boxing 是「one of the most common sources of unintended temporary memory
allocations」,並指出 C# 的 IDE 與編譯器不會對 boxing 發出警告
([Unity Manual 2022.3, Garbage collection best practices](https://docs.unity3d.com/2022.3/Documentation/Manual/performance-garbage-collection-best-practices.html);
另見 [Boxing and Unboxing (C#), Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/types/boxing-and-unboxing))。

刻意劃定的範圍界線:

- **值型別的 `new` 不回報**——struct 不在 managed 堆積上配置。
- **`throw new Exception(...)` 不回報**——例外路徑理應罕見;
  每幀丟例外是另一種 bug。
- **lambda 與閉包**屬於 UPA0007 的範圍;**字串串接與插值**屬於 UPA2000;
  方法群組(method group)產生的委派建立不在範圍內。
- **`params` 展開整批歸 UPA0027**——包含編譯器建立的陣列,以及進入該陣列的值型別裝箱。
  本規則早期版本會回報那些裝箱、只放過陣列;UPA0027 上線後,那會讓一筆配置產生兩條診斷。
  其他位置的裝箱仍由本規則回報。
- 同樣地,被 box 進字串串接的值型別(`"x" + n`)會由本規則回報,
  即使串接本身屬於 UPA2000。兩者是不同的配置,
  而 ZString 式的改寫可以一次消除兩者。
- 插值也是同樣的切分:值型別的插值洞(`$"hp {hp}"`)由本規則以 `boxed int`
  形式回報,而插值產生的字串本身屬於 UPA2000。字串型別的插值洞不回報。
  插值洞內的明確轉型(`$"{(object)hp}"`)改由 boxing 轉換路徑回報,
  因此每個插值洞只回報一次;運算式型別為型別參數(type parameter)的插值洞不回報。

這是本套件中觸發範圍最廣的規則。熱方法內的冷分支
(一次性的延遲初始化、罕見的除錯快照)即使很少執行也會被回報——
analyzer 不做流程分析。這些情況請使用下方的抑制選項。

## 如何修正

把配置提升到熱路徑之外,並重複使用該實例。

修正前:

```csharp
void Update()
{
    var results = new List<RaycastHit>();
    Scan(results);
}
```

修正後:

```csharp
readonly List<RaycastHit> _results = new List<RaycastHit>();

void Update()
{
    _results.Clear();
    Scan(_results);
}
```

對於 boxing,優先使用泛型多載(以 `Consume<T>(T value)` 取代
`Consume(object value)`)或泛型集合。

對於插值洞,把格式化提升到熱路徑之外並快取結果——只在值改變時重建字串:

修正前:

```csharp
void Update()
{
    hpLabel.text = $"hp {hp}";   // 每幀先 box hp,再配置字串
}
```

修正後(在變化時格式化,離開熱路徑):

```csharp
void OnHpChanged(int newHp)
{
    hpLabel.text = $"hp {newHp}";
}
```

或者改走明確不 boxing 的格式化路徑:`$"hp {hp.ToString()}"` 讓插值洞成為
字串型別(不 box;`ToString` 產生的字串本身屬於 UPA2000 的範圍),
而 ZString 這類泛型零垃圾格式化工具可以一次消除兩種配置。

## 何時抑制

在可證明極少執行的冷分支上(延遲初始化的守衛、僅供除錯的路徑),
或在特定位置採用池化/快取設計所增加的複雜度超過該配置的代價時,
可以抑制此警告。

## 如何設定或抑制

- 單一呼叫點:以 `#pragma warning disable UPA0006` / `#pragma warning restore UPA0006` 包住
- 整個專案:在 `.editorconfig` 設定 `dotnet_diagnostic.UPA0006.severity = suggestion`(或 `none`)
- 依路徑:隨附的 preset 已放寬 `[**/Editor/**/*.cs]` 下的規則;可為工具程式碼或產生的程式碼加入類似區段
- 熱路徑判定:調整下方的 `upa_hot_path_*` 選項

## 可設定項

熱路徑判定是共用的,可透過 `.editorconfig` 設定:

```ini
upa_hot_path_messages = Update,FixedUpdate,LateUpdate,OnTriggerEnter
upa_hot_path_attributes = HotPath,PerfCritical
upa_hot_path_include_lambdas = true
```

## 相關規則

- UPA0007 涵蓋捕捉式 lambda 造成的委派與閉包配置。
- UPA2000 涵蓋熱路徑上的字串串接與插值。
- UPA0027 涵蓋 `params` 展開,含編譯器建立的陣列內部的裝箱。
