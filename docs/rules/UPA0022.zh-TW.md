# UPA0022 — Enum.HasFlag in per-frame method

> [English](UPA0022.md) | 繁體中文

| | |
|---|---|
| 類別 | 效能 |
| 預設嚴重度 | 警告(Warning) |
| 預設啟用 | 是 |

## 成因

在每幀熱路徑內呼叫了 `System.Enum.HasFlag`。所謂每幀熱路徑,是指
`MonoBehaviour` 衍生型別上的熱門 Unity 訊息(如 `Update`、`FixedUpdate`、`LateUpdate`),
或標記了熱路徑屬性(如 `[HotPath]`)的方法。

## 規則說明

`HasFlag` 宣告在 `System.Enum` 基底類別上,其參數型別也是 `System.Enum`。
因此在 Unity 的 Mono 執行時期,對 enum 值呼叫它會把接收者與引數兩者都裝箱——
每次呼叫產生兩筆堆積配置,而手寫的等價檢查只需一個位元運算指令。
較新的 .NET 執行時期會把 `HasFlag` 視為 JIT intrinsic 並移除裝箱,
但該最佳化不適用於 Unity 的 Mono 執行時期,IL2CPP 的行為也隨 Unity 版本而異——
在 Unity 上應把這個呼叫視為會配置記憶體。

改寫不會損失任何行為:官方文件明載 `HasFlag` 的結果正是布林運算式
`(thisInstance & flag) == flag` ——
[Enum.HasFlag,Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/system.enum.hasflag)。
當 flag 引數為零時兩種寫法都回傳 `true`,所以改寫連這個邊界情況也保持一致。

只有熱路徑方法本身的主體(包含其中的 lambda 與區域函式)會被分析。
從熱路徑呼叫的輔助方法內部的呼叫刻意不回報——
本 analyzer 寧可漏報,也不誤報。

## 如何修正

把呼叫改寫為明確的位元檢查。本規則提供 code fix(「Use a bitwise check」),
會把 `x.HasFlag(y)` 改寫為 `(x & y) == y`。由於改寫會重複 flag 運算式,
只有當該運算式是常數、區域變數、參數或欄位時才提供 fix;若是方法呼叫或
屬性存取,請先把 flag 存入區域變數再手動改寫。

修正前:

```csharp
void Update()
{
    if (_state.HasFlag(UnitState.Stunned))
    {
        return;
    }
}
```

修正後:

```csharp
void Update()
{
    if ((_state & UnitState.Stunned) == UnitState.Stunned)
    {
        return;
    }
}
```

## 何時抑制

熱方法內可證明極少執行的冷分支(罕見狀態轉換、僅供除錯的路徑)可以就地抑制。

## 如何設定或抑制

- 單一呼叫點:以 `#pragma warning disable UPA0022` / `#pragma warning restore UPA0022` 包住
- 整個專案:在 `.editorconfig` 設定 `dotnet_diagnostic.UPA0022.severity = suggestion`(或 `none`)
- 依路徑:隨附的 preset 已放寬 `[**/Editor/**/*.cs]` 下的規則;可為工具程式碼或產生的程式碼加入類似區段
- 熱路徑判定:調整下方的 `upa_hot_path_*` 選項

## 可設定項

熱路徑判定是共用的,可透過 `.editorconfig` 設定:

```ini
upa_hot_path_messages = Update,FixedUpdate,LateUpdate,OnTriggerEnter
upa_hot_path_attributes = HotPath,PerformanceCritical
upa_hot_path_include_lambdas = true
```
