# UPA0026 — Value type boxed by inherited method call

> [English](UPA0026.md) | 繁體中文

| | |
|---|---|
| 類別 | 效能 |
| 預設嚴重度 | 警告(Warning) |
| 預設啟用 | 是 |

## 成因

在每幀熱路徑內(`MonoBehaviour` 衍生型別上的熱門 Unity 訊息,如 `Update`、
`FixedUpdate`、`LateUpdate`,或標記了熱路徑屬性如 `[HotPath]` 的方法),
以 struct 或 enum 為接收者呼叫 `GetType()`。

## 規則說明

`GetType()` 宣告在 `System.Object` 上且**無法被覆寫**,所以值型別沒有自己的實作可供分派。
CLR 的 constrained 呼叫規則寫明了替代做法:若值型別「does not implement `method` then
`ptr` is dereferenced, boxed, and passed as the 'this' pointer」——
[OpCodes.Constrained, Microsoft Learn](https://learn.microsoft.com/zh-tw/dotnet/api/system.reflection.emit.opcodes.constrained)。
那次裝箱是一次堆積配置,而換到的答案編譯器本來就知道。

IL2CPP player 實測,兩個支援的 Unity 版本皆然:以 struct 或 enum 為接收者的 `GetType()`
會配置,而同樣接收者上的 `ToString()`、`GetHashCode()`、`Equals(object)` **完全不配置**。

**在 Mono 上那三個確實會配置**——Unity 2022.3 每次 0.23 B、Unity 6 每次 1.11 B,
來自 constrained 呼叫的接收者裝箱。本套件的效能結論以 IL2CPP 為準(那是多數出貨遊戲實際跑的),
因此本規則不回報它們。Mono build 會付這個成本,而這裡不會告訴你;
替 struct 覆寫 `Equals` 與 `GetHashCode` 仍然值得做,理由見 `CA1815`。

### 本規則過去回報過的東西

在被實際量測之前,本規則也點名值型別未覆寫的 `ToString()`、`GetHashCode()` 與
`Equals(object)`,依據是上述的 constrained 呼叫規則,加上「移除該裝箱的 JIT 最佳化
不適用 Unity 的 Mono」。**推理本身沒問題,結論卻是錯的**:三者在 IL2CPP 上都讀到零,
而量測時已把引數在迴圈外先裝箱一次,使接收者成為迴圈內唯一可能配置的東西。

`value.Equals(other)` 中真正會配置的是**引數**——`Equals(object)` 的參數型別是 `object`,
所以運算元在呼叫處被裝箱。那是另一個位置的另一次轉換,由
[UPA0006](UPA0006.zh-TW.md) 在該處回報。

順帶一提,替 struct 覆寫 `Equals` 與 `GetHashCode` 仍然值得做,只是理由已不在本規則:
繼承來的實作以反射逐欄位比較與雜湊,即使不配置也很慢
([CA1815, Microsoft Learn](https://learn.microsoft.com/zh-tw/dotnet/fundamentals/code-analysis/quality-rules/ca1815));
而 struct 當作字典鍵卻沒有 `IEquatable<T>` 由 [UPA0028](UPA0028.zh-TW.md) 回報。

會與不會回報的情形:

- 接收者型別是泛型型別參數時**不回報**——constrained 呼叫會不會裝箱取決於實體化的型別。
- 參考型別接收者不回報:沒有東西需要裝箱。

只有熱路徑方法本身的主體(包含其中的 lambda 與區域函式)會被分析。
從熱路徑呼叫的輔助方法內部的呼叫刻意不回報——本分析器寧可漏報也不誤報。

## 如何修正

用 `typeof`。只要接收者的靜態型別已知,型別就是編譯期的事實——而那正是本規則會觸發的情形。

```csharp
// 修正前
void Update()
{
    var t = _cursor.GetType();   // 裝箱該 struct;答案在編譯期就已知
}

// 修正後
void Update()
{
    var t = typeof(Cursor);
}
```

若接收者的執行期型別確實與靜態型別不同,那它就不是值型別,本規則也不會回報。

### 關於 code fix

只要丟掉接收者不會改變執行內容,IDE 就會提供這個改寫:裸的區域變數、參數或欄位、`this`、
`this.欄位`,以及完全沒有寫接收者的情形。**更長的成員鏈不提供**——`holder.Value.GetType()`
會連 `holder` 為 null 時該擲的 `NullReferenceException` 一起丟掉,
`StaticHolder.Value.GetType()` 則會讓靜態建構不再執行。以下同樣不提供:

- **屬性**——getter 可以做任何事,而改寫會讓它不再被呼叫;
- **方法呼叫**——現在會求值一次,改寫後一次也不會;
- **索引存取**——改寫連可能擲出的邊界檢查一起拿掉;
- **可空值型別**——`((int?)x).GetType()` 在有值時回傳 `typeof(int)`,沒值時擲出
  `NullReferenceException`,沒有任何 `typeof` 寫法能同時保住這兩件事。

這些情形仍然會回報。先把接收者提到區域變數,或在你確認接收者可以安全丟掉之後自己寫下 `typeof`。

## 何時抑制

熱方法內可證明極少執行的冷分支——罕見狀態轉換,
或記錄與錯誤處理路徑——可以就地抑制。

## 如何設定或抑制

- 單一呼叫點:以 `#pragma warning disable UPA0026` / `#pragma warning restore UPA0026` 包住
- 整個專案:在 `.editorconfig` 設定 `dotnet_diagnostic.UPA0026.severity = suggestion`(或 `none`)
- 依路徑:隨附的 preset 已放寬 `[**/Editor/**/*.cs]` 下的規則;可為工具程式碼或產生的程式碼加入類似區段
- 熱路徑判定:調整下方的 `upa_hot_path_*` 選項

## 可設定項

熱路徑判定是共用的,可透過 `.editorconfig` 設定:

```ini
upa_hot_path_messages = Update,FixedUpdate,LateUpdate,OnTriggerEnter
upa_hot_path_attributes = HotPath,PerformanceCritical
upa_hot_path_include_lambdas = true
```
