# UPA0031 — Instantiate or Destroy in per-frame method

> English | [繁體中文](UPA0031.zh-TW.md)

| | |
|---|---|
| Category | Performance |
| Default severity | Warning |
| Enabled by default | Yes |

## Cause

`UnityEngine.Object.Instantiate` or `UnityEngine.Object.Destroy` is called inside a per-frame
hot path: a hot Unity message such as `Update`, `FixedUpdate` or `LateUpdate` on a
`MonoBehaviour`-derived type, or a method marked with a hot-path attribute such as
`[HotPath]`.

## Rule description

Creating an object costs more than allocating memory. Unity clones the source object's
components and serialised fields, wires up the new transform, and registers the result with
the scene. Destroying one does not free anything at that moment either — it marks the object
and leaves the collector to reclaim it later, which is precisely when a frame is most likely
to stutter.

Doing both every frame is the shape a pool exists to remove: create the objects once, hand
them out on demand, and take them back instead of destroying them.

The rule reports both halves under one id, with two different messages. They are two sides of
one decision, and the answer to both is the same. Splitting them into separate ids would let a
project silence one half and keep producing exactly as much garbage.

### What it matches

Matching is on the method symbol, never on how the call is written. Inside a `MonoBehaviour`
the usual form is:

```csharp
Instantiate(prefab);
```

There is no receiver in that line at all — the method is inherited from `UnityEngine.Object`.
An implementation that looked for `Object.Instantiate` as written would miss almost every real
occurrence, and would miss it without any sign that it had. The generic `Instantiate<T>` is
matched through the same declaring type.

## How to fix violations

Take the object from a pool and return it when it is finished:

```csharp
// Before
void Update()
{
    var bullet = Instantiate(bulletPrefab);
    // ...
    Destroy(bullet, 2f);
}

// After
void Update()
{
    var bullet = bulletPool.Get();
    // ...
    bulletPool.Release(bullet);   // after the same delay, from the bullet itself
}
```

Unity ships `UnityEngine.Pool.ObjectPool<T>` in 2021 and later; any pool with the same shape
works. Whatever you use, reset the object's state on the way out — reuse without a reset is
the bug this change most often introduces, and it does not look like one.

There is no code fix for this rule, deliberately. A pool needs a type, a capacity policy and a
point at which the object comes back, none of which can be read from the call site. A
mechanical rewrite would produce something that compiles, looks correct, and reuses instances
without resetting them.

## When to suppress warnings

- The object genuinely has to be new every time and cannot be reset — rare, but it happens
  with objects carrying identity that other systems hold references to.
- The hot method runs rarely in practice despite its name, for example an `Update` that
  returns immediately behind a flag and only does work on an event.
- The lifetime is bounded by something other than frames — one spawn per level, driven from
  `Update` only because that is where the input arrives.

## How to configure or suppress

The rule only reports inside hot paths, so the hot-path options control its scope:

```ini
upa_hot_path_messages = Update,FixedUpdate,LateUpdate
upa_hot_path_attributes = HotPath,PerformanceCritical
upa_hot_path_include_lambdas = true
```

Put these in `Rules.UnityPerformanceAnalyzers.additionalfile` for them to apply to Unity
builds; `.editorconfig` reaches the IDE only.

To change the severity for the whole project:

```ini
dotnet_diagnostic.UPA0031.severity = suggestion
```

## Related rules

- `UPA0006` reports allocations on a per-frame path generally. `Instantiate` is reported here
  instead, because the answer is a pool rather than hoisting the allocation.
- `DestroyImmediate` is **not** reported by this rule. It is worse on a hot path, but for a
  different reason — Unity documents that it should not be used at runtime at all — and this
  rule's advice would send you to a pool when the fix is to stop calling it.
