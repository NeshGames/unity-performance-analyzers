# UPA0014 — Scene-search API call in per-frame method

> English | [繁體中文](UPA0014.zh-TW.md)

| | |
|---|---|
| Category | Performance |
| Default severity | Warning |
| Enabled by default | Yes |

## Cause

A scene-search API is called inside a per-frame hot path: a hot Unity message such as
`Update`, `FixedUpdate`, or `LateUpdate` on a `MonoBehaviour`-derived type, or a method
marked with a hot-path attribute such as `[HotPath]`. The covered APIs are:

- `GameObject.Find`, `GameObject.FindWithTag`, `GameObject.FindGameObjectWithTag`,
  `GameObject.FindGameObjectsWithTag`
- `Object.FindObjectOfType`, `Object.FindObjectsOfType`, `Object.FindFirstObjectByType`,
  `Object.FindAnyObjectByType`, `Object.FindObjectsByType`

Matching is by declared type (`UnityEngine.GameObject` / `UnityEngine.Object`), so a
`Find` method you define on your own types is not reported.

The diagnostic message is:

> '{0}' searches the scene on every call and is not intended for per-frame use. Resolve the reference once in Awake or Start and cache it in a field.

where `{0}` is the qualified method name, for example `GameObject.Find`.

## Rule description

These APIs walk the scene hierarchy or the set of all loaded objects on every call, and
the result is not cached automatically — each call repeats the full search. Unity's own
documentation is direct about it: "`GameObject.Find` causes significant performance
degradation at scale and is not recommended for performance-critical code, especially in
`MonoBehaviour.Update`"
([Unity Scripting API, GameObject.Find](https://docs.unity3d.com/ScriptReference/GameObject.Find.html)).
The by-type family carries the same warning: `Object.FindFirstObjectByType` is described
as "very resource intensive", with the advice not to use it every frame
([Unity Scripting API, Object.FindFirstObjectByType](https://docs.unity3d.com/ScriptReference/Object.FindFirstObjectByType.html)).
The searched object rarely changes between frames, so repeating the search every frame
does redundant work that grows with scene size.

Only the body of the hot-path method itself (including its lambdas and local functions) is
analyzed. Calls inside helper methods invoked from a hot path are deliberately not reported
— this analyzer prefers missed reports over false positives.

## How to fix violations

Resolve the reference once in `Awake` or `Start`, cache it in a field, and use the field on
the hot path.

Before:

```csharp
public class Follower : MonoBehaviour
{
    void Update()
    {
        var player = GameObject.Find("Player");
        transform.LookAt(player.transform);
    }
}
```

After:

```csharp
public class Follower : MonoBehaviour
{
    Transform _player;

    void Start()
    {
        _player = GameObject.Find("Player").transform;
    }

    void Update()
    {
        transform.LookAt(_player);
    }
}
```

Where the target object is created and destroyed at runtime, prefer restructuring around
direct references — have the object register itself with a manager, or expose it through a
serialized field — instead of re-searching for it.

## When to suppress warnings

Suppress when the searched object genuinely changes between frames (for example, tagged
objects are spawned and destroyed at runtime and the current set must be re-resolved), or
when the call is on a cold branch that runs rarely despite being located in a hot method.

## How to configure or suppress

- Single call site: wrap it in `#pragma warning disable UPA0014` / `#pragma warning restore UPA0014`
- Whole project: set `dotnet_diagnostic.UPA0014.severity = suggestion` (or `none`) in `.editorconfig`
- By path: the shipped presets relax rules under `[**/Editor/**/*.cs]`; add similar sections for tooling or generated code
- Hot-path classification: adjust the `upa_hot_path_*` options below

## Configuration

The hot-path classification is shared and configurable via `.editorconfig`:

```ini
upa_hot_path_messages = Update,FixedUpdate,LateUpdate,OnTriggerEnter
upa_hot_path_attributes = HotPath,PerfCritical
upa_hot_path_include_lambdas = true
```
