# UPA0031 — Instantiate or Destroy in per-frame method

> [English](UPA0031.md) | 繁體中文

| | |
|---|---|
| 類別 | 效能 |
| 預設嚴重度 | 資訊(Info) |
| 預設啟用 | 是 |

## 成因

在逐幀熱路徑中呼叫 `UnityEngine.Object.Instantiate` 或 `UnityEngine.Object.Destroy`。
熱路徑指 `MonoBehaviour` 衍生型別上的 `Update`、`FixedUpdate`、`LateUpdate` 等 Unity 訊息,
或標註了 `[HotPath]` 之類熱路徑屬性的方法。

## 規則說明

建立一個物件的代價不只是配置記憶體。Unity 會複製來源物件的元件與序列化欄位、
接好新的 transform、再把結果登記進場景。銷毀也不會在當下釋放任何東西——
它只是標記該物件,把回收留給之後的 GC,而那正是一幀最容易卡頓的時機。

**本規則報的是位置,不是頻率,嚴重度也因此定在 Info。** 它比對的是「寫在逐幀方法裡的呼叫」;
那一行實際上是不是每幀執行,需要本規則不做的流程分析。在三個真實遊戲上,5 則發現**全部**
落在一次性守衛後面——過了生命期的飛彈、載入完成後銷毀自己的載入器。這其實不意外:
`Update` 裡沒有守衛的 `Destroy` 會在第一幀就把物件刪掉,在能跑的程式碼裡不可能存在。
規則保留,是因為它要找的形狀真實存在(按住開火鍵時每幀 `Instantiate`);評為 Info,
是因為證據撐不到更高。看到這則診斷時,請把它讀成「去確認這行多久跑一次」,
而不是「它每幀都在跑」。

每幀同時做這兩件事,正是物件池存在要消除的形狀:物件建立一次、需要時取出、
用完歸還而不是銷毀。

**兩半共用同一個編號,訊息不同。** 它們是同一個決定的兩面,答案也相同。
拆成兩個編號會讓專案關掉其中一半,而垃圾一點都沒少。

### 比對方式

判定看的是方法符號,**不看呼叫怎麼寫**。`MonoBehaviour` 內最常見的寫法是:

```csharp
Instantiate(prefab);
```

這一行**根本沒有接收者**——該方法繼承自 `UnityEngine.Object`。
若實作去找字面上的 `Object.Instantiate`,幾乎所有真實案例都會漏掉,
而且漏掉時毫無徵兆。泛型的 `Instantiate<T>` 由同一個宣告型別涵蓋。

## 如何修正

從池取出,用完歸還:

```csharp
// 修改前
void Update()
{
    var bullet = Instantiate(bulletPrefab);
    // ...
    Destroy(bullet, 2f);
}

// 修改後
void Update()
{
    var bullet = bulletPool.Get();
    // ...
    bulletPool.Release(bullet);   // 同樣延遲之後,由子彈自己歸還
}
```

Unity 2021 起內建 `UnityEngine.Pool.ObjectPool<T>`,任何同形狀的池都可以。
不論用哪一種,**取出時要重設物件狀態**——重用而不重設是這個改動最常引入的錯誤,
而且它看起來不像錯誤。

**本規則刻意不提供 CodeFix。** 池需要型別、容量策略、以及物件何時回來,
這三者都無法從呼叫點讀出。機械式重寫會產生一段可編譯、看起來正確、
但重用實例卻沒有重設的程式碼。

## 何時應該抑制

- 物件確實每次都必須是新的且無法重設——少見,但當其他系統持有該物件的參考、
  物件帶有身分意義時會發生
- 該熱路徑方法實際上很少執行:例如 `Update` 開頭就依旗標提早返回,只在事件發生時才做事
- 生命週期由別的東西界定而非幀:每關生成一次,寫在 `Update` 只是因為輸入從那裡來

## 如何設定或抑制

本規則只在熱路徑內報告,因此熱路徑選項就是它的範圍控制:

```ini
upa_hot_path_messages = Update,FixedUpdate,LateUpdate
upa_hot_path_attributes = HotPath,PerformanceCritical
upa_hot_path_include_lambdas = true
```

要讓設定對 **Unity build** 生效,請寫在 `Rules.UnityPerformanceAnalyzers.additionalfile`;
`.editorconfig` 只到得了 IDE。

調整全專案嚴重度:

```ini
dotnet_diagnostic.UPA0031.severity = suggestion
```

## 相關規則

- `UPA0006` 泛稱地報告逐幀路徑上的配置。`Instantiate` 改由本規則負責,
  因為它的答案是物件池,而不是把配置提到迴圈外
- **`DestroyImmediate` 不由本規則報告。** 它在熱路徑上更糟,但理由不同——
  Unity 明載它不該在執行期使用——而本規則的建議會把你指向物件池,
  真正的修法卻是別再呼叫它
