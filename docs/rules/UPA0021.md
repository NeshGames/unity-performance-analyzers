# UPA0021 — magnitude or Distance compared where sqrMagnitude suffices

> English | [繁體中文](UPA0021.zh-TW.md)

| | |
|---|---|
| Category | Performance |
| Default severity | Warning |
| Enabled by default | Yes |

## Cause

A relational comparison (`<`, `<=`, `>`, `>=`) where exactly one side is a
`Vector2` / `Vector3` / `Vector4` `magnitude` property access or a static
`Vector2.Distance(...)` / `Vector3.Distance(...)` / `Vector4.Distance(...)` call:

```csharp
if (transform.position.magnitude < 5f) { ... }
if (Vector3.Distance(a, b) < radius) { ... }
```

Comparisons with a magnitude or `Distance` expression on **both** sides are not reported
— both sides take a square root, so the rewrite preserves the comparison but saves
nothing. Equality operators are also out of scope; the rewrite only preserves meaning for
ordering comparisons against a squared threshold.

## Rule description

`magnitude` and the `Distance` methods compute a square root. When the result is only
compared against a threshold, the square root is wasted work: "Calculating the squared
magnitude instead of using the magnitude property is much faster - the calculation is
basically the same only without the slow Sqrt call. If you are using magnitudes simply to
compare distances, then you can just as well compare squared magnitudes against the
squares of distances since the comparison will give the same result" —
[Unity Scripting API, Vector3.sqrMagnitude](https://docs.unity3d.com/ScriptReference/Vector3-sqrMagnitude.html).

The rule is not limited to per-frame hot paths — distance checks concentrate in gameplay
code that tends to run per frame anyway, and the rewrite costs nothing in readability.

The diagnostic message reads: "Comparing '{0}' computes a square root. Compare
sqrMagnitude against the squared threshold instead."

## How to fix violations

Compare `sqrMagnitude` against the squared threshold:

Before:

```csharp
if (transform.position.magnitude < 5f) { ... }
if (Vector3.Distance(a, b) < radius) { ... }
```

After:

```csharp
if (transform.position.sqrMagnitude < 25f) { ... }
if ((a - b).sqrMagnitude < radius * radius) { ... }
```

A code fix ("Compare sqrMagnitude against the squared threshold") is offered when the
non-magnitude side is a plain numeric literal: it rewrites `v.magnitude` to
`v.sqrMagnitude`, rewrites `Vector3.Distance(a, b)` to `(a - b).sqrMagnitude`, and
squares the literal (`5f` becomes `25f`). A plain literal is non-negative by
construction; a negative threshold is written with a unary minus (`-1f`), and that shape
gets no fix, because squaring it would change the comparison's meaning. Non-literal
thresholds (fields, parameters, expressions) also get no automatic fix — square them by
hand, as in the `radius * radius` example.

## When to suppress warnings

Suppress when the threshold is a runtime value that can be negative — for example, a
signed configuration value where `magnitude > threshold` is intended to hold for every
vector once the threshold drops below zero. Squaring such a threshold changes the
comparison's meaning, so the reported rewrite does not apply. Cold, clarity-first code
(editor tooling, one-shot validation) is also a reasonable place to keep `magnitude`.

## How to configure or suppress

- Single call site: wrap it in `#pragma warning disable UPA0021` / `#pragma warning restore UPA0021`
- Whole project: set `dotnet_diagnostic.UPA0021.severity = suggestion` (or `none`) in `.editorconfig`
- By path: the shipped presets relax rules under `[**/Editor/**/*.cs]`; add similar sections for tooling or generated code
