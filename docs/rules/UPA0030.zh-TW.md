# UPA0030 — Known-allocating BCL API in per-frame method

> [English](UPA0030.md) | 繁體中文

| | |
|---|---|
| 類別 | 效能 |
| 預設嚴重度 | 警告(Warning) |
| 預設啟用 | 是 |

## 成因

在每幀熱路徑內呼叫了一份封閉清單上的 .NET 基礎類別庫成員——這些成員每次呼叫都會配置。
熱路徑指 `MonoBehaviour` 衍生型別上的熱門 Unity 訊息(`Update`、`FixedUpdate`、
`LateUpdate` 等),或標記了熱路徑屬性(如 `[HotPath]`)的方法。

| 成員 | 配置內容 | 替代方案 |
|---|---|---|
| `string.Split` | 陣列 + 每個子字串 | `ReadOnlySpan<char>` 切片,或快取結果 |
| `string.ToCharArray` | `char[]` | 同上 |
| `string.Substring` | 字串 | 同上 |
| `string.ToLower` / `ToLowerInvariant` / `ToUpper` / `ToUpperInvariant` | 字串 | 改用 `StringComparison.OrdinalIgnoreCase` 比較,不要轉換大小寫 |
| `string.Trim` / `TrimStart` / `TrimEnd` | 字串,**且僅在真的有東西可修剪時** | `ReadOnlySpan<char>.Trim`,或把呼叫移出熱路徑 |
| `Enum.GetValues` / `Enum.GetNames` | 陣列 | 快取在 `static readonly` 欄位 |

## 規則說明

判斷任意方法會不會配置需要跨方法的逃逸分析。在本套件所鎖定的 Roslyn 版本上成本很高,
而且準確度不足以據此回報。所以本規則**不做推論**:改為檢查一份策劃過的清單,
其中每一項的配置行為都是有文件、可驗證的事實——以覆蓋率換取零誤報。

清單背後的依據:

- [`System.String`](https://learn.microsoft.com/dotnet/api/system.string) 是不可變型別,
  所以每個看似修改字串的操作實際上都回傳新實例。
- [`Enum.GetValues`](https://learn.microsoft.com/dotnet/api/system.enum.getvalues)
  每次呼叫回傳新陣列,這正是「快取起來」成為標準建議的原因。

每一項在列入前也都在本專案的 sandbox 實測過:Unity 2022.3 與 Unity 6,涵蓋 Mono 與 IL2CPP。
量測產生了一個值得知道的但書:**`Trim` 在沒有東西可修剪時回傳原實例**,該情形不配置。
規則仍會回報,因為字串內容在編譯期不可知——但如果你到 profiler 上找不到那筆配置,原因在此。

清單刻意保持封閉。項目是逐一、且先經量測後才加入的,而不是靠放寬比對規則擴張——
這正是誤報維持在零的原因。若你預期會出現的成員不在清單上,那是可以回報的缺口,
不是需要繞過的疏漏。

有相同問題的 UnityEngine 成員歸 UPA0018。這條分界——BCL 在這裡、`UnityEngine.*` 在那裡——
正是讓同一個呼叫不會被兩條規則各報一次的原因。

## 如何修正

把不會變的東西快取起來:

修正前:

```csharp
void Update()
{
    foreach (var name in Enum.GetNames(typeof(State)))
    {
        Draw(name);
    }
}
```

修正後:

```csharp
static readonly string[] StateNames = Enum.GetNames(typeof(State));

void Update()
{
    foreach (var name in StateNames)
    {
        Draw(name);
    }
}
```

不分大小寫的比較,直接比較而不要轉換:

```csharp
// 修正前:兩個運算元各配置一份小寫副本
if (a.ToLowerInvariant() == b.ToLowerInvariant()) { }

// 修正後:零配置
if (string.Equals(a, b, StringComparison.OrdinalIgnoreCase)) { }
```

至於每幀都在做的字串剖析,通常的答案是**不要每幀做**:資料進來時剖析一次並保留結果。

## 何時抑制警告

熱方法內證實極少執行的冷分支、編輯器工具程式碼,或配置量很小而直接寫法的可讀性
比那點垃圾更值錢時。

存量專案第一次開啟本規則,可能會一次冒出不少 `Substring` 與 `ToLower` 的回報。
先以 `warning` 跑一個版本再考慮升 `error`,是合理的處理節奏。

## 如何設定或抑制

- 單一呼叫點:以 `#pragma warning disable UPA0030` / `#pragma warning restore UPA0030` 包住
- 整個專案:於 `.editorconfig` 設定 `dotnet_diagnostic.UPA0030.severity = suggestion`(或 `none`)
- 依路徑:內附 preset 已對 `[**/Editor/**/*.cs]` 放寬
- 熱路徑判定:調整下方 `upa_hot_path_*` 選項

## 設定

熱路徑判定為共用設定,可經 `.editorconfig` 調整:

```ini
upa_hot_path_messages = Update,FixedUpdate,LateUpdate,OnTriggerEnter
upa_hot_path_attributes = HotPath,PerfCritical
upa_hot_path_include_lambdas = true
```

## 相關規則

- UPA0018 負責會配置陣列的 `UnityEngine.*` 成員。兩份清單不交集:新項目依「屬於什麼」
  歸位,而不是依「什麼時候加的」。
- UPA0013 負責熱路徑上的 LINQ 使用,含 `ToArray` 與 `ToList`。它們刻意不在本清單裡——
  把它們放在一條預設開啟的規則裡,等於繞過「LINQ 回報屬選擇性啟用」這項設計。
- UPA0022 負責 `Enum.HasFlag`;UPA0026 負責 `Enum.ToString` 造成的裝箱。
- `UNT0018`(Microsoft.Unity.Analyzers)負責 Unity 訊息內的反射,所以 `System.Type`
  的反射成員不列在這裡。
