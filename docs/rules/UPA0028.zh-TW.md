# UPA0028 — Value type used as collection key without IEquatable

> [English](UPA0028.md) | 繁體中文

| | |
|---|---|
| 類別 | 效能 |
| 預設嚴重度 | 警告(Warning) |
| 預設啟用 | 是 |

## 成因

struct 被當作雜湊集合的 key —— `Dictionary<TKey, TValue>`、`HashSet<T>`、
`ConcurrentDictionary<TKey, TValue>` —— 或在 `List<T>` / 陣列上以 `Contains`、`IndexOf`、
`Remove`、`Array.IndexOf`、`Array.Contains` 搜尋,而該 struct 未同時實作 `IEquatable<T>`
與覆寫 `GetHashCode`。

與本專案多數效能規則不同,本規則**不限熱路徑**:key 設計不良的字典,查詢在哪裡都一樣貴。

## 規則說明

[`EqualityComparer<T>.Default`](https://learn.microsoft.com/dotnet/api/system.collections.generic.equalitycomparer-1.default)
依型別選擇實作:它「uses the `IEquatable<T>` generic interface … if type `T` implements it」。
有實作的 struct 會拿到呼叫具型別 `Equals` 的比較器,不配置;沒實作的則拿到呼叫
`object.Equals(object)` 的版本,每次比較把兩個運算元各裝箱一次。

若該 struct 連 `Equals` 都沒覆寫會更糟:繼承來的
[`ValueType.Equals`](https://learn.microsoft.com/dotnet/api/system.valuetype.equals)
會對非 blittable 欄位以反射「field by field」逐欄位比較——不只配置,還慢。
`GetHashCode` 同理,所以兩者都要做:只做一項,每次查詢仍有成本。

本專案在 sandbox 實測過:Unity 2022.3 與 Unity 6,涵蓋 Mono 與 IL2CPP。
20 萬次 `ContainsKey` 中,純資料 struct 解析到 `ObjectEqualityComparer<T>` 且確有配置
(執行期間 gen0 回收 9–20 次);同一個 struct 加上 `IEquatable<T>` 與 `GetHashCode` 覆寫後
解析到 `GenericEqualityComparer<T>`,零配置。

**enum 不回報。** 同一批量測確認執行時期對 enum 有專用的非裝箱比較器——
見[Enum 作字典 key](enum-dictionary-keys.zh-TW.md)。型別參數也不回報,
因為是否裝箱取決於實體化型別。

診斷回報在**使用點**,並以 struct 宣告作為附加位置。struct 宣告處無法得知它是否被當作
key 使用,回報在那裡會讓真正的問題淹沒在對純資料 struct 的無效建議裡。

## 如何修正

在 struct 上實作兩個成員。

修正前:

```csharp
public struct GridCoord
{
    public int X;
    public int Y;
}

readonly Dictionary<GridCoord, Tile> tiles = new Dictionary<GridCoord, Tile>();
```

修正後:

```csharp
public readonly struct GridCoord : IEquatable<GridCoord>
{
    public readonly int X;
    public readonly int Y;

    public bool Equals(GridCoord other) => X == other.X && Y == other.Y;

    public override bool Equals(object obj) => obj is GridCoord other && Equals(other);

    public override int GetHashCode()
    {
        unchecked
        {
            return (X * 397) ^ Y;
        }
    }
}
```

`System.HashCode.Combine` 寫起來更乾淨,但可用性取決於專案的 API Compatibility Level,
上面的質數乘法寫法在所有設定下都能用。

若無法修改該 struct(例如來自第三方套件),改為在集合建構時傳入
`IEqualityComparer<T>`。有傳入 comparer 的建立運算式不會被回報。

## 何時抑制警告

集合很小且生命週期短時,或該 struct 是無法修改的第三方型別、而自備 comparer 不划算時。

## 如何設定或抑制

- 單一位置:以 `#pragma warning disable UPA0028` / `#pragma warning restore UPA0028` 包住
- 整個專案:於 `.editorconfig` 設定 `dotnet_diagnostic.UPA0028.severity = suggestion`(或 `none`)
- 依路徑:注意內附的 `editor-relaxed` preset **刻意保留**本規則的嚴重度——
  程式碼在編輯器端,不會讓 struct 更適合當 key

## 設定

無。本規則沒有選項,也不限熱路徑。

## 相關規則

- `CA1815` 要求所有 public struct 覆寫 `Equals` 與 `operator ==`,不論用途,
  且不要求 `IEquatable<T>`。本規則只在 struct **實際被當作 key** 時觸發。
  啟用本規則時建議把 `CA1815` 設為 `none`。
- UPA0026 回報在值型別上直接呼叫繼承的 `ToString`/`GetHashCode`/`Equals(object)` 造成的裝箱。
  兩者不重疊:那裡的裝箱呼叫看得見寫在你的程式碼裡;這裡則發生在集合內部。
- [Enum 作字典 key](enum-dictionary-keys.zh-TW.md) 說明本建議的 enum 版本為何已不適用。
