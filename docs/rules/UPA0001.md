# UPA0001 — Component lookup in per-frame method

> English | [繁體中文](UPA0001.zh-TW.md)

| | |
|---|---|
| Category | Performance |
| Default severity | Warning |
| Enabled by default | Yes |

## Cause

A `GetComponent`-family method (`GetComponent`, `GetComponents`, `GetComponentInChildren`,
`GetComponentsInChildren`, `GetComponentInParent`, `GetComponentsInParent`, or
`TryGetComponent` — any generic or non-generic overload, on either
`UnityEngine.Component` or `UnityEngine.GameObject`) is called inside a per-frame hot path:
a hot Unity message such as `Update`, `FixedUpdate`, or `LateUpdate` on a
`MonoBehaviour`-derived type, or a method marked with a hot-path attribute such as
`[HotPath]`.

## Rule description

Component lookups are implemented in Unity's native engine code. Every call crosses the
managed–native boundary and searches the object's component list before returning a result.
The lookup result does not change unless components are added or removed, so repeating the
search every frame does redundant work.

`TryGetComponent` is often recommended for avoiding an allocation, and that is an Editor-only
difference: Unity documents `GetComponent` as allocating "when it's executed in the Editor,
but not in a built project", and a player build measures no allocation for either. So
`TryGetComponent` is reported as well — the cost this rule is about is the native call and
the type search, which both forms pay. Cache the result instead.

Only the body of the hot-path method itself (including its lambdas and local functions) is
analyzed. Calls inside helper methods invoked from a hot path are deliberately not reported
— this analyzer prefers missed reports over false positives.

## How to fix violations

Resolve the component once in `Awake` or `Start`, cache it in a field, and use the field on
the hot path.

Before:

```csharp
public class Mover : MonoBehaviour
{
    void Update()
    {
        GetComponent<Rigidbody>().AddForce(Vector3.up);
    }
}
```

After:

```csharp
public class Mover : MonoBehaviour
{
    Rigidbody _rigidbody;

    void Awake()
    {
        _rigidbody = GetComponent<Rigidbody>();
    }

    void Update()
    {
        _rigidbody.AddForce(Vector3.up);
    }
}
```

## When to suppress warnings

Suppress when the component set genuinely changes between frames (for example, components
are added or removed at runtime and the current instance must be re-resolved), or when the
call is on a cold branch that runs rarely despite being located in a hot method.

## How to configure or suppress

- Single call site: wrap it in `#pragma warning disable UPA0001` / `#pragma warning restore UPA0001`
- Whole project: set `dotnet_diagnostic.UPA0001.severity = suggestion` (or `none`) in `.editorconfig`
- By path: the shipped presets relax rules under `[**/Editor/**/*.cs]`; add similar sections for tooling or generated code
- Hot-path classification: adjust the `upa_hot_path_*` options below

## Configuration

The hot-path classification is shared and configurable via `.editorconfig`:

```ini
upa_hot_path_messages = Update,FixedUpdate,LateUpdate,OnTriggerEnter
upa_hot_path_attributes = HotPath,PerformanceCritical
upa_hot_path_include_lambdas = true
```

## Related rules

- `UNT0026` (Microsoft.Unity.Analyzers) flags `GetComponent` results that are never null
  checked, regardless of the calling context. The two rules coexist: UPA0001 only fires on
  hot paths.
