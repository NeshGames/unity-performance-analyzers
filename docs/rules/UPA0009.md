# UPA0009 — List Count not hoisted out of for loop

> English | [繁體中文](UPA0009.zh-TW.md)

| | |
|---|---|
| Category | Performance |
| Default severity | Warning |
| Enabled by default | No |

## Cause

The condition of a `for` loop on a per-frame hot path reads
`System.Collections.Generic.List<T>.Count`, and the loop body does not mutate the same
list.

## Rule description

`List<T>.Count` is a property read that repeats on every iteration. When the list size
does not change inside the loop, hoisting the count into a local before the loop removes
that repeated read — a micro-optimization that is only worth enforcing on hot paths, which
is why this rule is **disabled by default** and enabled by the `strict` preset.

Boundaries drawn to avoid wrong or misleading reports:

- **Arrays are excluded.** `i < array.Length` is the exact form the JIT recognizes to
  eliminate bounds checks; hoisting `Length` can make array loops *slower*.
- **A loop that could change the list** is excluded — hoisting there would change
  semantics. That covers more than `Add`/`Remove`/`Clear` on the receiver; see
  [What this rule cannot see](#what-this-rule-cannot-see) for every route it treats as a
  possible mutation.
- **Receiver matching is shallow**: a bare identifier or `this.identifier` (the two are
  treated as the same receiver). Deeper chains such as `a.b.Count` are never reported,
  because mutation of those cannot be judged reliably.

## How to fix violations

Before:

```csharp
void Update()
{
    for (int i = 0; i < _weights.Count; i++)
    {
        _total += _weights[i];
    }
}
```

After:

```csharp
void Update()
{
    int count = _weights.Count;
    for (int i = 0; i < count; i++)
    {
        _total += _weights[i];
    }
}
```

## What this rule cannot see

Hoisting `Count` is only correct while the collection does not change during the loop, so the
rule stays quiet whenever the loop could reach the collection by any route other than reading
it. That means the initializer and the incrementor as well as the body — the initializer runs
before the hoisted read would, so a mutation there changes how many times the loop runs: calling anything on it, passing it as an argument, assigning it to something else, or
using it to initialise a declaration. The call case does not look at the method name: a
closed list of mutating names is what an extension method walks straight past. Reading through it — `list.Count`, `list[i]` — cannot produce
another reference, so those still report.

It also stays quiet on the routes that never name the collection at all:

- **Replacing it.** `items = GetMore();` (or `this.items = …`, or a deconstruction that
  assigns it) leaves the loop reading a different list from the one the hoisted count
  came from.
- **A call into the type that owns it**, when the receiver is a field or property. Any
  method called through `this` — implicitly, as `Kill(_enemies[i])`, or written out as
  `this.Kill(…)` — can reach the field, as can a static method of the same type for a
  static field, and anything handed `this` as an argument — a constructor included,
  `new Watcher(this)`. `Kill` removing from `_enemies` is the ordinary shape of this, and
  nothing at the call site shows it.
- **A property or indexer of the same instance**, for the same reason: an accessor is a
  method written as a read or an assignment. `CurrentTarget = _targets[i];` whose setter
  drops the old target from `_targets`, or `Health -= damage;` whose setter clears the list
  at zero. Auto-properties (`{ get; set; }`) only store a value and still report. Properties
  compiled into another assembly, such as Unity's, cannot be read: reading one still
  reports (`transform` does not call back into your script), writing one does not
  (`enabled = false` runs `OnDisable` before it returns).
- **A local function or any delegate call.** A local function may have captured the list
  wherever it was declared, including outside the loop; a delegate may be a lambda that
  did, or a subscriber that removes itself. That holds however the delegate is called —
  `OnHit(x)`, `OnHit?.Invoke(x)`, `callback.Invoke(x)`, or a delegate field of another
  object.

These are judged by what *could* reach the list, not by reading the callee, so a loop that
calls one of its own type's methods is not reported even when that method is harmless. A
list held in a local is out of reach of the type's methods, so those loops still report.

One case remains and cannot be removed. Another object may already hold the collection and
mutate it from inside the loop:

```csharp
for (int i = 0; i < items.Count; i++)
{
    spawner.Refill();      // spawner was handed `items` in Awake
}
```

Nothing at this call site says so. If your loop body calls into code that owns the same
collection, do not hoist.

## When to suppress warnings

Suppress when the list is mutated indirectly (through a method call the analyzer cannot
see) inside the loop — hoisting would then be incorrect — or when profiling shows the read
is irrelevant.

## How to configure or suppress

- Enable the rule (it is off by default): `<Rule Id="UPA0009" Action="Warning" />` in `Assets/Default.ruleset`
- Single call site: wrap it in `#pragma warning disable UPA0009` / `#pragma warning restore UPA0009`
- Whole project: set `<Rule Id="UPA0009" Action="None" />` in `Assets/Default.ruleset`
- Hot-path classification: adjust the `upa_hot_path_*` options below

## Configuration

The hot-path classification is shared and set in the universal options file `Assets/Rules.UnityPerformanceAnalyzers.additionalfile` (the same `key = value` lines also work in an `.editorconfig` passed to `upa-cli --editorconfig`):

```ini
upa_hot_path_messages = Update,FixedUpdate,LateUpdate,OnTriggerEnter
upa_hot_path_attributes = HotPath,PerformanceCritical
upa_hot_path_include_lambdas = true
```
