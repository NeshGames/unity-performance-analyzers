# UPA0017 — 逐幀方法內使用回傳陣列的 GetComponents 多載

> [English](UPA0017.md) | 繁體中文

| | |
|---|---|
| 類別 | 效能 |
| 預設嚴重度 | 警告(Warning) |
| 預設啟用 | 是 |

## 成因

在逐幀熱路徑內呼叫了 `GetComponents`、`GetComponentsInChildren` 或
`GetComponentsInParent` 的回傳陣列多載(不論定義在 `UnityEngine.Component` 或
`UnityEngine.GameObject` 上)。所謂逐幀熱路徑,是指 `MonoBehaviour` 衍生型別上的
熱門 Unity 訊息(如 `Update`、`FixedUpdate`、`LateUpdate`),或標記了熱路徑屬性
(如 `[HotPath]`)的方法。

只有回傳陣列的多載會被回報。接受 `List<T>` 的多載回傳 `void`、
填入呼叫端提供的 list,因此不會被回報。

診斷訊息為:

> '{0}' allocates a new array on every call. Use the List&lt;T&gt; overload with a list cached in a field instead.

其中 `{0}` 是方法名稱,例如 `GetComponentsInChildren`。

## 規則說明

回傳陣列的多載每次呼叫都會配置一個新的 managed 陣列。這是回傳陣列的 Unity API 的
一般性契約——「all Unity APIs that return arrays create a new copy of the array each
time they're accessed」
([Unity Manual,Garbage collection best practices](https://docs.unity3d.com/2022.3/Documentation/Manual/performance-garbage-collection-best-practices.html))——
因此每幀呼叫會穩定產生與符合數量成正比的垃圾。

Unity 正是為了這種情境提供 `List<T>` 多載:提供的 list 會被調整為結果數量、
先前內容被覆寫,依 API 文件的說法,這「allows you to avoid allocating new List
objects for each call to the method」
([Unity Scripting API,Component.GetComponents](https://docs.unity3d.com/ScriptReference/Component.GetComponents.html))。
把 list 快取在欄位後,一旦 list 成長到穩定容量,每幀的配置就完全消失。

本規則沒有自動 code fix:正確的修法是引入可重複使用的 `List<T>` 欄位,
這是型別層級的變更,不是呼叫點的改寫。

只有熱路徑方法本身的主體(包含其中的 lambda 與區域函式)會被分析。
從熱路徑呼叫的輔助方法內部的呼叫刻意不回報——
本 analyzer 寧可漏報,也不誤報。

## 如何修正

改用 `List<T>` 多載,並把 list 快取到欄位。

修正前:

```csharp
public class ColliderScanner : MonoBehaviour
{
    void Update()
    {
        foreach (var collider in GetComponentsInChildren<Collider>())
        {
            Process(collider);
        }
    }
}
```

修正後:

```csharp
public class ColliderScanner : MonoBehaviour
{
    readonly List<Collider> _colliders = new List<Collider>();

    void Update()
    {
        GetComponentsInChildren(_colliders);
        foreach (var collider in _colliders)
        {
            Process(collider);
        }
    }
}
```

若元件組合不會在幀與幀之間變動,可考慮在 `Awake` 或 `Start` 解析一次,
而不是每幀重新查詢。

## 何時抑制

當該呼叫位於熱方法中但實際上極少執行的冷分支上,或回傳的陣列刻意要離開該方法
(被儲存起來,或交給會取得所有權的 API)、共用 list 會造成錯誤時,可以抑制。

## 如何設定或抑制

- 單一呼叫點:以 `#pragma warning disable UPA0017` / `#pragma warning restore UPA0017` 包住
- 整個專案:在 `.editorconfig` 設定 `dotnet_diagnostic.UPA0017.severity = suggestion`(或 `none`)
- 依路徑:隨附的 preset 已放寬 `[**/Editor/**/*.cs]` 下的規則;可為工具程式碼或產生的程式碼加入類似區段
- 熱路徑判定:調整下方的 `upa_hot_path_*` 選項

## 可設定項

熱路徑判定是共用的,可透過 `.editorconfig` 設定:

```ini
upa_hot_path_messages = Update,FixedUpdate,LateUpdate,OnTriggerEnter
upa_hot_path_attributes = HotPath,PerfCritical
upa_hot_path_include_lambdas = true
```
