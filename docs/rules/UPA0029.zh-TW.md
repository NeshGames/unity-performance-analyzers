# UPA0029 — Sequential Add replaceable with AddRange

> [English](UPA0029.md) | 繁體中文

| | |
|---|---|
| 類別 | 效能 |
| 預設嚴重度 | 警告(Warning) |
| 預設啟用 | 是 |

## 成因

迴圈把一個可計數的來源逐個元素複製到另一個集合,而單一次 `AddRange` 呼叫能以一次配置
完成同樣的事。

兩種形式都會回報:

```csharp
foreach (var item in source)
    target.Add(item);

for (int i = 0; i < source.Count; i++)
    target.Add(source[i]);
```

## 規則說明

`List<T>` 以倍增方式成長。容量不足時它配置一個新的後備陣列並把全部元素複製過去,
所以逐個加入 N 個元素可能觸發 `O(log N)` 次重新配置與複製——
[`List<T>.Capacity`](https://learn.microsoft.com/dotnet/api/system.collections.generic.list-1.capacity)
說明成長策略,而
[`AddRange`](https://learn.microsoft.com/dotnet/api/system.collections.generic.list-1.addrange)
以事先保留空間避開它。

**但只在來源可被計數時成立。** 那正是讓 `AddRange` 得以事先保留空間的前提;
面對一般的 `IEnumerable<T>`,它就是列舉並逐個加入,跟原本的迴圈一模一樣。
這是多數談這條建議的文章漏掉的條件,也是「真的有改善」與「白改一場」的分界,
所以對 LINQ 查詢或迭代器方法的迴圈不會回報。

來源還必須是**陣列或 `List<T>`**,而不只是某個 `ICollection<T>`。
`List<T>.AddRange` 會走 `Count` + `CopyTo` 的快速路徑,而它取代的迴圈走的是 `GetEnumerator`;
自訂集合完全可以讓這兩者在順序或內容上不一致。只有框架型別能確定兩條路徑行為相同。

除此之外觸發條件刻意收得很窄:迴圈主體必須是對迭代元素本身的單一次 `Add` ——
沒有投影、沒有成員存取、沒有過濾、沒有其他陳述式。任何一項都會改變迴圈的語意,
而 `AddRange` 不會重現它。索引形式另外要求從 0 開始、步進為 1、索引只使用一次、
且以來源自身的 `Count`/`Length` 為界;不符合的迴圈就不是完整複製。

目標必須是元素型別能接受該來源的 `List<T>`。複製到 `HashSet<T>` 不回報(沒有 `AddRange`),
自訂集合即使剛好宣告了一個也不回報:手寫的 `AddRange` 完全可以做出與逐個 `Add` 不同的事,
而且只檢查「方法存在」還會放行 `Add(int)` 與 `AddRange(IEnumerable<string>)` 對不上的型別,
產出編不過的改寫。

另有兩項限制,因為改寫必須語意相同:

- **來源與目標都必須是穩定的參考**——區域變數、參數、欄位,或這些構成的鏈。
  `GetTarget().Add(item)` 每次迭代都會重新求值,可能每次回傳不同的集合,
  收合成一次呼叫會改變元素的去向。索引形式的來源同理:界限與元素存取都是每次迭代求值。

  **屬性不算穩定**,自動屬性也不算。getter 每次存取可能回傳不同的集合、或有副作用,
  而符號上沒有任何資訊能區分自動屬性與計算屬性——來自參考組件的屬性尤其如此。
  所以 `foreach (var x in holder.Items) target.Add(x)` 不會被回報。
  這確實損失了覆蓋率,是刻意的取捨:會動手改你程式碼的規則,必須確定自己是對的。
  想讓規則看見,先把集合指派給區域變數。
- **兩者不得是同一個集合。** `foreach (var x in items) items.Add(x)` 今天會擲出例外
  (列舉期間集合被修改),其索引形式則永不終止;而 `items.AddRange(items)` 兩者都不會發生。
  把壞掉的程式碼變成能跑的程式碼仍然是行為變更,不該由自動修正靜默完成。

有一種情形是任何符號比對都抓不到的:兩個不同的變數在執行期指向同一個集合。
這正是本規則不附 CodeFix 的原因——見「如何修正」。

## 如何修正

把迴圈換成單一次呼叫:

修正前:

```csharp
foreach (var spawn in spawnPoints)
    active.Add(spawn);
```

修正後:

```csharp
active.AddRange(spawnPoints);
```

**改之前先確認兩者不是同一個 list。** 若是同一個,你手上的迴圈會擲例外或永不終止,
而 `AddRange` 兩者都不會發生——那是要修的 bug,不是要最佳化的配置。

本規則**不附 CodeFix**,原因正是如此:兩個不同的參考可能在執行期指向同一個 list,
任何符號比對都排除不了;而一個會把當機靜默變成「行為不同」的修正,不值得提供。
改寫只有一行,判斷它安全才是需要人來做的部分。

## 何時抑制警告

集合確定很小時,或迴圈是為了可讀性而這樣寫、且只在啟動時跑一次時——
重新配置的成本要有規模才顯現。

## 如何設定或抑制

- 單一位置:以 `#pragma warning disable UPA0029` / `#pragma warning restore UPA0029` 包住
- 整個專案:於 `.editorconfig` 設定 `dotnet_diagnostic.UPA0029.severity = suggestion`(或 `none`)
- 依路徑:內附 preset 已對 `[**/Editor/**/*.cs]` 放寬
- 收窄至逐幀程式碼:設定下方選項

## 設定

預設在任何位置回報複製迴圈。要限制在逐幀程式碼:

```ini
upa_addrange_hot_path_only = true
```

此選項也可寫在 `Rules.UnityPerformanceAnalyzers.additionalfile`,其優先序高於
`.editorconfig`,而且那才是 Unity 本身會讀的檔案。

啟用該選項後,熱路徑判定為共用設定:

```ini
upa_hot_path_messages = Update,FixedUpdate,LateUpdate,OnTriggerEnter
upa_hot_path_attributes = HotPath,PerfCritical
upa_hot_path_include_lambdas = true
```

## 相關規則
