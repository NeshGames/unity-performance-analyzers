# UPA0009 — List Count not hoisted out of for loop

> [English](UPA0009.md) | 繁體中文

| | |
|---|---|
| 類別 | Performance |
| 預設嚴重度 | Warning |
| 預設啟用 | 否 |

## 成因

位於每幀熱路徑上的 `for` 迴圈,其條件式讀取了
`System.Collections.Generic.List<T>.Count`,且迴圈本體並未修改同一個 list。

## 規則說明

`List<T>.Count` 是一次屬性讀取,每次迭代都會重複執行。當 list 的大小在迴圈內不會改變時,
在迴圈前先把 count 提出到區域變數,即可消除這個重複讀取——這是一項只有在熱路徑上才值得
強制執行的微最佳化,因此本規則**預設停用**,由 `strict` preset 啟用。

為避免錯誤或誤導性的回報,劃定了以下邊界:

- **陣列不在範圍內。**`i < array.Length` 正是 JIT 用來消除邊界檢查所辨識的形式;
  把 `Length` 提出反而可能讓陣列迴圈*變慢*。
- **可能改變 list 的迴圈**不在範圍內——在那種情況下提出 count 會改變語意。
  範圍不只是對接收者呼叫 `Add`、`Remove`、`Clear`;規則視為「可能改動」的所有途徑,
  見[這條規則看不到什麼](#這條規則看不到什麼)。
- **接收者比對採淺層規則**:只認裸識別字或 `this.identifier`(兩者視為同一個接收者)。
  更深的鏈式存取如 `a.b.Count` 一律不回報,因為無法可靠判斷其是否被修改。

## 如何修正

修正前:

```csharp
void Update()
{
    for (int i = 0; i < _weights.Count; i++)
    {
        _total += _weights[i];
    }
}
```

修正後:

```csharp
void Update()
{
    int count = _weights.Count;
    for (int i = 0; i < count; i++)
    {
        _total += _weights[i];
    }
}
```

## 這條規則看不到什麼

把 `Count` 提到迴圈外,只有在迴圈期間集合不改變時才正確。因此只要迴圈有**任何**
讀取以外的途徑碰到該集合——**含初始式與遞增式,不只迴圈體**(初始式在提升後的讀取之前執行,
在那裡改動集合會改變迴圈跑幾次)——對它呼叫任何東西、當引數傳出、指派給別的東西、或用來初始化宣告——規則就不報。呼叫那一項**不看方法名**:封閉的「會改動」名單正是擴充方法能直接走過去的地方。
透過它讀取(`list.Count`、`list[i]`)不會產生另一個參考,那些仍然回報。

完全不提到該集合的途徑,規則同樣不報:

- **替換它。**`items = GetMore();`(或 `this.items = …`,或以解構指派它)之後,迴圈讀的
  已經是另一個 list,而提出去的 count 屬於原本那個。
- **呼叫擁有它的型別**(接收者是欄位或屬性時)。任何經由 `this` 呼叫的方法——隱含的
  `Kill(_enemies[i])` 或明寫的 `this.Kill(…)`——都碰得到該欄位;靜態欄位則同型別的靜態方法
  也碰得到;把 `this` 當引數傳出去也一樣,建構子也算(`new Watcher(this)`)。`Kill` 從
  `_enemies` 移除元素正是這種情形的典型寫法,呼叫點上看不出來。
- **同一個實例的屬性或索引子**,理由相同:存取子就是寫成讀取或指派的方法。
  `CurrentTarget = _targets[i];` 的 setter 會把舊目標從 `_targets` 移除,
  `Health -= damage;` 的 setter 會在歸零時清空 list。自動屬性(`{ get; set; }`)只存值,
  仍然回報。編譯在其他組件裡的屬性(例如 Unity 的)讀不到內容:讀取仍然回報
  (`transform` 不會回呼你的腳本),寫入則不回報(`enabled = false` 會在返回前執行 `OnDisable`)。
- **區域函式,或任何委派呼叫。**區域函式不論宣告在哪(包括迴圈外)都可能捕獲了該 list;
  委派則可能是捕獲了它的 lambda,或是會把自己移除的訂閱者。不論委派怎麼呼叫都一樣——
  `OnHit(x)`、`OnHit?.Invoke(x)`、`callback.Invoke(x)`,或別的物件上的委派欄位。

這些是依「可能碰到 list」判斷,而不是去讀被呼叫端,所以迴圈只要呼叫了自己型別的方法就不回報,
即使那個方法無害。存在區域變數裡的 list,型別的方法碰不到,那些迴圈仍然回報。

有一種情形無法消除:別的物件早已持有該集合,並在迴圈中改動它。

```csharp
for (int i = 0; i < items.Count; i++)
{
    spawner.Refill();      // spawner 在 Awake 時就拿到了 items
}
```

呼叫點上沒有任何東西看得出這件事。**若迴圈體會呼叫到持有同一個集合的程式碼,不要提出去。**

## 何時抑制

當 list 在迴圈內被間接修改(透過 analyzer 看不見的方法呼叫)——此時提出 count 反而是錯的——
或當 profiling 顯示這個讀取無關緊要時,可以抑制。

## 如何設定或抑制

- 啟用本規則(預設為關閉):在 `Assets/Default.ruleset` 設定 `<Rule Id="UPA0009" Action="Warning" />`
- 單一呼叫位置:以 `#pragma warning disable UPA0009` / `#pragma warning restore UPA0009` 包住
- 整個專案:在 `Assets/Default.ruleset` 設定 `<Rule Id="UPA0009" Action="None" />`
- 熱路徑判定:調整下方的 `upa_hot_path_*` 選項

## 可設定項

熱路徑判定為共用設定,設定在通用選項檔 `Assets/Rules.UnityPerformanceAnalyzers.additionalfile`(同樣的 `key = value` 行也可寫進透過 `upa-cli --editorconfig` 傳入的 `.editorconfig`):

```ini
upa_hot_path_messages = Update,FixedUpdate,LateUpdate,OnTriggerEnter
upa_hot_path_attributes = HotPath,PerformanceCritical
upa_hot_path_include_lambdas = true
```
