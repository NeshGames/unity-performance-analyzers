# UPA0014 — 逐幀方法內呼叫場景搜尋 API

> [English](UPA0014.md) | 繁體中文

| | |
|---|---|
| 類別 | 效能 |
| 預設嚴重度 | 警告(Warning) |
| 預設啟用 | 是 |

## 成因

在逐幀熱路徑內呼叫了場景搜尋 API。所謂逐幀熱路徑,是指 `MonoBehaviour` 衍生型別上的
熱門 Unity 訊息(如 `Update`、`FixedUpdate`、`LateUpdate`),或標記了熱路徑屬性
(如 `[HotPath]`)的方法。涵蓋的 API 為:

- `GameObject.Find`、`GameObject.FindWithTag`、`GameObject.FindGameObjectWithTag`、
  `GameObject.FindGameObjectsWithTag`
- `Object.FindObjectOfType`、`Object.FindObjectsOfType`、`Object.FindFirstObjectByType`、
  `Object.FindAnyObjectByType`、`Object.FindObjectsByType`

比對是以宣告型別為準(`UnityEngine.GameObject` / `UnityEngine.Object`),
因此你在自己型別上定義的 `Find` 方法不會被回報。

診斷訊息為:

> '{0}' searches the scene on every call and is not intended for per-frame use. Resolve the reference once in Awake or Start and cache it in a field.

其中 `{0}` 是完整方法名稱,例如 `GameObject.Find`。

## 規則說明

這些 API 每次呼叫都會走訪場景階層或所有已載入的物件,且結果不會被自動快取——
每次呼叫都會重複完整搜尋。Unity 官方文件的說法很直接:「`GameObject.Find` causes
significant performance degradation at scale and is not recommended for
performance-critical code, especially in `MonoBehaviour.Update`」
([Unity Scripting API,GameObject.Find](https://docs.unity3d.com/ScriptReference/GameObject.Find.html))。
依型別搜尋的家族也有相同的警告:`Object.FindFirstObjectByType` 被描述為
「very resource intensive」,並建議不要每幀使用
([Unity Scripting API,Object.FindFirstObjectByType](https://docs.unity3d.com/ScriptReference/Object.FindFirstObjectByType.html))。
被搜尋的物件在幀與幀之間極少變動,因此每幀重複搜尋是在做多餘的工作,
而且成本會隨場景規模成長。

只有熱路徑方法本身的主體(包含其中的 lambda 與區域函式)會被分析。
從熱路徑呼叫的輔助方法內部的呼叫刻意不回報——
本 analyzer 寧可漏報,也不誤報。

## 如何修正

在 `Awake` 或 `Start` 中解析引用一次,快取到欄位,並在熱路徑上使用該欄位。

修正前:

```csharp
public class Follower : MonoBehaviour
{
    void Update()
    {
        var player = GameObject.Find("Player");
        transform.LookAt(player.transform);
    }
}
```

修正後:

```csharp
public class Follower : MonoBehaviour
{
    Transform _player;

    void Start()
    {
        _player = GameObject.Find("Player").transform;
    }

    void Update()
    {
        transform.LookAt(_player);
    }
}
```

若目標物件會在執行期建立與銷毀,建議改以直接引用重構——讓物件向管理者註冊自己,
或透過 serialized 欄位公開——而不是反覆搜尋它。

## 何時抑制

當被搜尋的物件確實會在幀與幀之間變動(例如帶標籤的物件會在執行期生成與銷毀,
必須重新解析目前的集合),或該呼叫位於熱方法中但實際上極少執行的冷分支上時,
可以抑制此警告。

## 如何設定或抑制

- 單一呼叫點:以 `#pragma warning disable UPA0014` / `#pragma warning restore UPA0014` 包住
- 整個專案:在 `.editorconfig` 設定 `dotnet_diagnostic.UPA0014.severity = suggestion`(或 `none`)
- 依路徑:隨附的 preset 已放寬 `[**/Editor/**/*.cs]` 下的規則;可為工具程式碼或產生的程式碼加入類似區段
- 熱路徑判定:調整下方的 `upa_hot_path_*` 選項

## 可設定項

熱路徑判定是共用的,可透過 `.editorconfig` 設定:

```ini
upa_hot_path_messages = Update,FixedUpdate,LateUpdate,OnTriggerEnter
upa_hot_path_attributes = HotPath,PerfCritical
upa_hot_path_include_lambdas = true
```

## 相關規則
