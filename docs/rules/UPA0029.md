# UPA0029 — Sequential Add replaceable with AddRange

> English | [繁體中文](UPA0029.zh-TW.md)

| | |
|---|---|
| Category | Performance |
| Default severity | Warning |
| Enabled by default | Yes |

## Cause

A loop copies a countable source into another collection one element at a time, where a
single `AddRange` call would do the same work with one allocation.

Two shapes are reported:

```csharp
foreach (var item in source)
    target.Add(item);

for (int i = 0; i < source.Count; i++)
    target.Add(source[i]);
```

## Rule description

`List<T>` grows by doubling. When capacity runs out it allocates a new backing array and
copies everything across, so adding N elements one at a time can reallocate and copy O(log N)
times — [`List<T>.Capacity`](https://learn.microsoft.com/dotnet/api/system.collections.generic.list-1.capacity)
describes the growth, and
[`AddRange`](https://learn.microsoft.com/dotnet/api/system.collections.generic.list-1.addrange)
avoids it by reserving the space up front.

**But only when the source can be counted.** That is what lets `AddRange` reserve the space;
given a plain `IEnumerable<T>` it enumerates and adds one at a time, exactly like the loop
did. This is the condition most write-ups of this advice leave out, and it is the difference
between a real improvement and a pointless rewrite, so a loop over a LINQ query or an
iterator method is not reported.

The source must also be an **array or a `List<T>`**, not merely some `ICollection<T>`.
`List<T>.AddRange` takes a fast path through `Count` and `CopyTo`, while the loop it replaces
goes through `GetEnumerator`; a custom collection is free to make those two disagree, in
order or in content. Only the framework types are known to behave the same either way.

The trigger is deliberately narrow beyond that. The loop body must be a single `Add` of the
iteration element itself — no projection, no member access, no filter, no extra statements.
Anything else changes what the loop means, and `AddRange` would not reproduce it. The indexed
form additionally requires starting at zero, stepping by one, using the index once, and
bounding by the source's own `Count`/`Length`; a loop that does otherwise is not a full copy.

The target must be a `List<T>` whose element type accepts the source. Copying into a
`HashSet<T>` is not reported — no `AddRange` — and neither is a custom collection that
happens to declare one: a hand-written `AddRange` is free to do something other than what
repeated `Add` calls do, and checking only that the method exists would also let through a
type whose `Add(int)` and `AddRange(IEnumerable<string>)` do not line up, producing a
rewrite that does not compile.

Two further restrictions exist because the rewrite has to mean the same thing:

- **Source and target must both be stable references** — a local, parameter, field, or a
  chain of those. `GetTarget().Add(item)` is re-evaluated on every iteration and may hand
  back a different collection each time, so collapsing it into one call would change where
  the elements go. The same applies to an indexed source, whose bound and element access are
  both evaluated per iteration.

  **Properties do not count as stable**, including auto-properties. A getter may return a
  different collection on each access or have side effects, and nothing in the symbol
  distinguishes an auto-property from a computed one — least of all for a property that came
  from a referenced assembly. So `foreach (var x in holder.Items) target.Add(x)` is not
  reported. That is a real loss of coverage, accepted deliberately: a rule that offers to
  rewrite your code has to be right about it. Assign the collection to a local first if you
  want the rule to see it.
- **They must not be the same collection.** `foreach (var x in items) items.Add(x)` throws
  today, because the collection is modified while it is being enumerated, and its indexed
  form never terminates. `items.AddRange(items)` quietly does neither. Turning broken code
  into working code is still a behaviour change, and not one a fix should make silently.

One case remains that no amount of symbol comparison can catch: two distinct variables that
refer to the same collection at runtime. That is why this rule ships without a code fix — see
"How to fix violations".

## How to fix violations

Replace the loop with a single call:

Before:

```csharp
foreach (var spawn in spawnPoints)
    active.Add(spawn);
```

After:

```csharp
active.AddRange(spawnPoints);
```

**Check first that the two are not the same list.** If they are, the loop you have throws or
never terminates, and `AddRange` would quietly do neither — that is a bug to fix, not an
allocation to optimize.

There is no automatic fix for this rule, and that is why: two distinct references can point
at the same list at runtime, no symbol comparison can rule it out, and a fix that silently
turns a crash into different behaviour is not one worth offering. The rewrite is one line;
deciding it is safe is the part that needs a person.

## When to suppress warnings

Suppress when the collection is known to be tiny, or when the loop is written that way for
readability in code that runs once at startup — the reallocations only add up at scale.

## How to configure or suppress

- Single site: wrap it in `#pragma warning disable UPA0029` / `#pragma warning restore UPA0029`
- Whole project: set `dotnet_diagnostic.UPA0029.severity = suggestion` (or `none`) in `.editorconfig`
- By path: the shipped presets relax rules under `[**/Editor/**/*.cs]`
- Narrow it to per-frame code: set the option below

## Configuration

By default this rule reports copy loops anywhere. To limit it to per-frame code:

```ini
upa_addrange_hot_path_only = true
```

The option can also live in `Rules.UnityPerformanceAnalyzers.additionalfile`, which takes
precedence over `.editorconfig` and is what Unity itself reads.

With the option enabled, the hot-path classification is the shared one:

```ini
upa_hot_path_messages = Update,FixedUpdate,LateUpdate,OnTriggerEnter
upa_hot_path_attributes = HotPath,PerformanceCritical
upa_hot_path_include_lambdas = true
```

## Related rules

- UPA0013 reports LINQ use on hot paths. A loop over a LINQ query is not reported by this
  rule, because `AddRange` would not help there — but the query itself may be worth removing.
