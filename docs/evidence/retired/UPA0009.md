# Retired evidence — UPA0009 List.Count hoist

UPA0009 was retired in AF-05B. Its live analyzer, tests, resources, preset rows and rule pages
were removed; the diagnostic ID remains permanently reserved in `RetiredRuleIds`.

## Unity IL2CPP measurement

The sandbox measures a 64-item `List<T>` loop with the count read in the condition and with the
count hoisted to a local. The committed measurement files report:

| Runtime | `i < list.Count` | hoisted `count` | difference per 64-item loop |
|---|---:|---:|---:|
| Unity 2022.3 IL2CPP | 108.96 ns | 98.62 ns | 10.34 ns |
| Unity 6 IL2CPP | 105.06 ns | 99.52 ns | 5.54 ns |

Source measurements:

- `sandbox/UnityProject/Measurements/allocation-2022.3.62f2-IL2CPP-NET_Standard_2_0.txt`
- `sandbox/UnityProject/Measurements/allocation-6000.5.3f1-IL2CPP-NET_Standard_2_0.txt`

The Unity 6 gain is real but about 5.5 ns for the entire 64-iteration loop, roughly 0.09 ns per
iteration.

## Why the diagnostic was removed

Making this rewrite safe required a disproportionately large analyzer: roughly 26 KB of analyzer
source plus roughly 16 KB of dedicated tests. It had to reason conservatively about mutations in
the initializer, incrementor and body; aliases; calls on the owning type; properties and indexers;
delegates; local functions; and reassignment.

Even that analysis cannot see a pre-existing alias held by another object:

```csharp
for (int i = 0; i < items.Count; i++)
{
    spawner.Refill(); // spawner may already hold and mutate items
}
```

Hoisting `Count` in that case can change program behaviour. For an agent-first analyzer suite,
the maintenance and rewrite-risk surface is not justified by a ~5.5 ns gain per 64-item loop.
Profile genuinely hot loops instead of enforcing this micro-optimization repository-wide.
